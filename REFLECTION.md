# Chapter 4 — Reflection (Final Frozen Agent)

**Evidence:** 91 matched runs from `final_standard.csv` (13 conditions × 7 scenarios, one round), plus the preceding 91-run `standard.csv` submitted alongside it. Metrics below refer to automated *tool-policy compliance*; human factuality/helpfulness/naturalness scores have not been supplied.

## 1. Which persona gave the most helpful or natural results?

For a student-facing tutoring assistant, I would select **Noura — Friendly Advisor**. In the inspected responses, it explained service policies in accessible language and frequently followed with a practical invitation to continue, which suits students and parents better than a purely formal answer. It passed **7/7** tool-policy checks. The **Strict Academic Expert** was useful for concise, source-oriented pricing and eligibility explanations, while the **Cautious Helper** communicated a more measured tone for customer details and follow-up; each passed **6/7**. Their single failure was the undocumented scholarship question, where neither invoked `record_feedback`. This is my qualitative preference based on the stored responses, not a claim of statistically measured naturalness: the CSV's three human-rating fields remain empty. The dry-run confirmation messages are also less natural than normal customer-facing replies.

## 2. Which prompt and configuration combination performed best for your use case?

The best **practical default** was Friendly Advisor with direct instructions, a few-shot worked example, and persona instructions in the system message, using its configured temperature of **0.6** and `gpt-4.1-mini`. This baseline achieved **7/7** on the seven tool-policy scenarios. It tied with brief-step guidance, temperature 0.2, frequency penalty 0.5, presence penalty 0.5, and a 250-token completion limit. In contrast, zero-shot, in-message instructions, temperature 0.9, top-p 0.65, and compact instructions each obtained 6/7 because the agent skipped recording the undocumented scholarship question. I prefer the baseline over tied alternatives because its prompt structure is simple and its conversational wording is appropriate for the target audience. The experiment used one run per condition and seven cases, so I cannot conclude that a particular hyperparameter is consistently superior. The "brief_steps" condition tested concise, structured step-planning against direct instructions. This is **CoT-inspired but not an exact hidden-chain-of-thought ablation**, which is a limitation relative to the assignment's explicit CoT comparison requirement.

## 3. How well did your agent reason and use tools?

The manual LangGraph ReAct cycle worked as intended: a reasoning node selected whether to answer or request a tool; my Python code executed the selected action and returned an observation; the next model step formed the response. The final run completed **91/91** scenarios with no API/runtime errors and achieved **84/91 (92.3%)** automated tool-policy matches. All 13 multi-step pricing cases calculated $100 for four separate lessons, $90 for the package and $10 savings, while rejecting the Sunday 8 PM request. The agent withheld lead storage in all 13 no-consent cases and successfully validated the lead-writing tool in all 13 explicit-consent cases. Complaints were handled by `record_feedback` in all conditions. The main weakness was unanswered-policy escalation: only **6/13** conditions recorded the unknown scholarship question. Importantly, passing the tool-use proxy did not guarantee a fully informative answer. Some simulated write confirmations reported only that nothing had actually been stored, omitting the requested policy explanation.

## 4. Did your instructions block change the agent's behavior noticeably? How?

Yes, though not uniformly. The full operational instructions separated the agent's persona from concrete requirements: cite official information, avoid inventing policies or bookings, request scoped permission before storing contact data, record complaints/unanswered questions, and interpret tool observations. On the matched final test set, **full instructions passed 7/7** versus **6/7** with compact instructions; **few-shot/system placement passed 7/7**, while zero-shot/system and few-shot/in-message each passed **6/7**. Those small differences arose from whether `record_feedback` was called for an undocumented policy, not from errors in basic pricing or subject eligibility. Comparing the **two CSVs committed to the repository**, the policy-match rate rose from **77/91 (84.6%)** in `standard.csv` to **84/91 (92.3%)** in `final_standard.csv`—seven more matches. Because multiple implementation components changed, this cannot be attributed exclusively to prompt changes. The experiment suggests instructions help express operational intent but do not guarantee that the model or its self-checker applies it correctly.

## 5. What were the biggest implementation challenges?

The hardest issue was **the gap between natural-language interpretation and safe tool execution**. My earlier consent validator accepted only narrow wording, rejecting a valid sentence that explicitly granted permission. Instead of adding more phrases to a whitelist, I redesigned consent interpretation to consider the conversation and scope of permission, while retaining deterministic checks for email format and whether a write could occur. The final experiment passed all explicit-consent scenarios, although the one-turn test set does not establish performance on every informal multi-turn reply. The second challenge was **distinguishing missing source evidence from a definite negative policy**. Several personas answered that no scholarship was documented but failed to log the unresolved question. Even when I added semantic source-coverage verification, both checks sometimes labeled the question as resolved; this showed that agreement among LLM judges is not necessarily reliable. A third challenge was **truthful side-effect reporting**: in dry-run experiments, a successful tool validation must not be described as a real customer record or guaranteed staff follow-up. Additional verification contributed to **370 model calls** in the final run compared with **305** in the preceding committed `standard.csv`. The recorded mean latency, however, decreased from **6.45 s** to **4.60 s** across those runs; network and execution conditions were not controlled sufficiently to attribute latency changes to a single design decision. Overall, this assignment showed me that building an agent is not only about generating convincing text: it requires traceable actions, evidence-based uncertainty, privacy-preserving validation, and an evaluation that separates operational success from response quality.
